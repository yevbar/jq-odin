# 0021: Number addition primitive

- Status: proposed
- Date: 2026-08-02
- Workstream: value

## Context and evidence

jq's polymorphic `binop_plus` has a number/number branch that calls
`jv_number_value` on both operands, adds the resulting C `double`s, constructs
the result with `jv_number`, and only then releases both consumed inputs
(`upstream/jq/src/builtin.c:82-102`). Under USE_DECNUM, `jv_number_value`
lazily converts a literal payload to binary64 by reducing it under a 17-digit
decimal64 context, generating decimal text, and passing that text to
`jvp_strtod`; a native number is read directly
(`upstream/jq/src/jv.c:601-620,699-712`). `jv_number` always creates an inline
native representation (`upstream/jq/src/jv.c:674-683`). Therefore numeric `+`
does not call decNumber addition and never returns a retained decimal payload,
even for literal plus literal.

Literal creation separately allocates a decimal payload, parses with jq's
`DEC_INIT_BASE` context, and caches neither result spelling nor binary64 until
requested (`upstream/jq/src/jv.c:508-523,533-599`). Literal output lazily uses
`decNumberToString`; native output uses binary64 formatting, maps NaN to null,
and clamps infinities to `DBL_MAX` before formatting
(`upstream/jq/src/jv.c:623-683`; `upstream/jq/src/jv_print.c:253-277`). The
manual explicitly says all numeric arithmetic produces a double-precision
result, while an unmutated literal can retain its form
(`upstream/jq/docs/content/manual/v1.8/manual.yml:643-651`). The jq tests likewise
state that arithmetic truncates to double and probe literal-to-double conversion
with `.+0` (`upstream/jq/tests/jq.test:2152-2167,2198-2205`). decNumber parsing
does apply context precision, exponent, rounding, overflow, and underflow before
the cached conversion (`upstream/jq/vendor/decNumber/decNumber.c:461-478,687-706,7310-7383`),
but no decNumber arithmetic or finalization occurs during `+` itself.

Thus the public libjq API accepts explicit signs and signaling spellings for
payload-free NaNs, but canonicalizes all of them to the positive quiet NaN
with zero payload before addition. The Odin constructor initially returned
`math.nan_f64()`, which was independently observed as
`7ff8000000000001` on this target. The constructor now uses jq's exact
canonical bits; finite parsing, nonzero-payload rejection, and native NaN
selection remain unchanged.

both operands are NaNs, preserves the selected sign/payload, and quiets a
selected signaling NaN. The initial Odin implementation was independently
reproduced with:

bits (for example, expected `fff8000000000099` but got
`7ff8000000000042`). That is Odin/platform code-generation behavior and did
not match the pinned jq oracle.

## Decision

`number_add(left, right: ^Value) -> (Value, bool)` is the public Value-level
numeric primitive. Both operands are borrowed for the complete call. Nil,
invalid, or any non-number operand returns an inert Value and `false`; both
operands remain unchanged. Two numbers return a separately owned inline native
Value and `true`. There is no error handle because this operation has no
allocation or cleanup failure boundary: `false` means operand rejection, and
`true` means a complete allocation-free result.

For literal+literal, literal+native, native+literal, and native+native, each
operand is first observed as its binary64 value. If neither operand is NaN,
ordinary target binary64 addition is performed without any result rewriting.
If exactly one operand is NaN, that operand's sign and payload are selected;
if both are NaNs, the right operand's sign and payload are selected. The
selected NaN is quieted by setting its binary64 quiet bit. All four
representation combinations return inline native storage and
allocate zero bytes. The API accepts no allocator; source allocator provenance
is irrelevant to result construction and no allocator callback is made.
Consequently nil-success, short-success, explicit allocation failure,
mismatched-allocation cleanup/retry, and bulk-retirement behavior are
unreachable. The inline result's final destruction is infallible and makes no
allocator call. Existing fallible destruction still governs independently
allocated source literals.

For two non-NaN operands, the result follows the target's IEEE-754 binary64
addition for rounding, precision, subnormals, underflow, overflow, infinities,
signed zero, and infinity-generated NaNs.
Exact cancellation in the default rounding mode produces positive zero;
negative zero plus negative zero produces negative zero. Constructible native
NaNs instead use the explicit jq-compatible selection above, avoiding
platform/compiler-dependent operand choice without canonicalizing the selected
sign or payload. Compact output therefore uses native spelling: NaN becomes
`null`, infinity is clamped to the maximum finite binary64 spelling, negative
zero prints `-0`, and every retained decimal spelling/precision style is lost.
Repeated and chained calls round after every binary64 addition.

`left == right` is valid because both operands are borrowed. Retained shallow
clones are also valid. Neither source is consumed, cloned, retained, mutated,
or released, and source/result owners may be destroyed in any order. The
result never aliases either source. Implementations and callers must not copy a
live owning `Value` with ordinary Odin assignment; this procedure reads numeric
scalars and constructs the result through `number_value`.

This is not jq's polymorphic `+`: null identity and string, array, and object
addition remain evaluator/builtin work outside this slice.

## Consequences

The public Value API gains one borrowed, allocation-free primitive without a
new Error kind, allocator parameter, package, or import edge. Current json,
program, compiler, and eval consumers require no change. A future evaluator
may call this primitive only after it has selected jq's number/number branch;
it remains responsible for jq's consumed evaluator operands and polymorphic
type errors.

## Validation

Focused tests cover operand rejection, all representation pairs, exact result
kind and binary64 bits, precision and exponent boundaries, overflow,
underflow, signed zero, infinities, sole-NaN propagation, both signed and
distinct-payload two-NaN orders, signaling-to-quiet behavior, native/literal
NaN pairs, unmodified infinity-generated NaNs, repeated addition, aliasing,
retained clones, both destruction orders, zero allocator activity under forced
allocation/free failure, and inline result destruction. The full Value suite
runs with allocation tracking and the required build/thread/sanitizer matrix,
followed by `make validate`.

Required independent review lanes are source-aware decNumber/binary64 semantic
parity, Odin ownership and allocator-fault safety, and test-gap falsification.
